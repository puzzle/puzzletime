PuzzleTime — daisyUI as a possible next step

What a migration to daisyUI would look like after the asset pipeline upgrade is finished — the order of operations, what the existing architecture already buys us, and the three decisions that have to be made rather than discovered.

Companion to upgrade.html · branch task/65394-ruby-and-rails-upgrade · written 2026-08-14 · not a committed plan — an evaluation

daisyUI is a visual redesign, not a compatibility layer. It will not look like Bootstrap 3, and making it look like Bootstrap 3 means re-authoring exactly the hand-written CSS that phases 5–6 exist to delete. Design sign-off is a precondition, not a step.

That is the constraint the question doesn't state, and everything below assumes it has been answered yes.

The layer architecture already built for Bootstrap → Tailwind is what makes Bootstrap → daisyUI incremental. @layer theme, base, bootstrap, components, utilities (§4.1) is exactly the right shape: daisyUI emits into components and therefore outranks whatever bootstrap-frozen.css still holds — for free, with no !important and no re-ordering. The same per-component loop, the same gates, the same bisectability.

1. Step 1 — layer the app SCSS blocks everything else

Wrap the compiled app SCSS in a named layer ranked after components

Goal: a daisyUI component class actually reaches the element it is on.

puzzletime.scss and friends style .btn, .table and .form-control directly, unlayered, across ~6000 lines. Unlayered CSS beats every layered rule regardless of source order or specificity (§4.1) — so today, every daisyUI component would be silently fought by an invisible override, and the symptom is a component that looks half-applied with nothing in the markup to explain it.

§7's risk table already anticipates this and calls it a nuisance to fix when it becomes one. Under daisyUI it stops being a nuisance and becomes the thing that defeats the library. So it moves to the front:

@layer theme, base, bootstrap, components, app, utilities;
/*                                          ^^^ compiled application.css goes here */

Two properties worth buying at the same time:

  • Give app-authored component overrides their own layer rather than relying on source order inside components to sit above @plugin "daisyui". Then "who wins" is answerable by reading the one @layer statement, instead of hunting import order in a file that grows.
  • The shims written in phase 5 keep working unchanged either way — they are already in components.

This is commit one, before any daisyUI class exists. It is also independently useful: it is the same commit whether or not daisyUI ever lands.

2. Step 2 — toolchain spike 10 minutes

tailwindcss-rails ~> 4.6 runs the standalone tailwindcss-ruby binary. Whether it resolves @plugin "daisyui" out of node_modules decides whether step 2 is one line of CSS or a small toolchain change. Find out by trying it, not by reasoning about it — and do it before writing any of the rest down, because it is the only unknown that can change the shape of the plan.

OutcomeThen
The standalone binary loads the plugin @plugin "daisyui"; in app/assets/tailwind/application.css, plus npm i -D daisyui. Nothing else moves.
It does not Drop tailwindcss-rails and drive Tailwind from the npm CLI instead. Nearly free here: npm, esbuild and Node-in-the-Docker-build-image all landed in phase 2, and Procfile.dev already has a tailwind: line to repoint.

Either way this blocks step 3, not the plan.

3. Step 3 — one theme, from the @theme block we already have

daisyUI's whole design system is a set of semantic CSS custom properties. The §4.4 @theme block already carries the Puzzle palette in exactly that form, so this step is a transcription, not a decision:

  • Map the brand colours onto daisyUI's semantic tokens (primary / success / info / warning / error / the base surface scale) and the radius tokens.
  • One custom theme, marked default; the ~30 built-in themes off. Shipping them is dead CSS and invites someone to add a theme switcher nobody asked for.
  • Keep the @theme block as the source of values — the remaining SCSS reads the same var(--color-…), which is the consolidation §4.4 already describes as opportunistic.

4. Step 4 — build the class map by installing, not from memory

Do not write the Bootstrap → daisyUI mapping table from recall. daisyUI renamed and removed classes between its v4 and v5, and a wrong mapping table in a planning document does not get questioned — it gets executed. Install the package, dump the class list it actually emits, and diff that against the §6 catalogue. That is a mechanical half-day and it produces a table that is true.

What can be asserted without the package installed, because it is structural rather than nominal:

ShapeWhy it matters
Shared names, different meanings The exact mirror of §4.3, one level up: while bootstrap-frozen.css and daisyUI coexist, btn, alert, table, label, checkbox, radio, progress and modal are all claimed by both and will double-style. The layer order decides who wins, which is why step 1 comes first — but "wins" is not the same as "looks right", so each of these needs eyes.
label is the sharpest Bootstrap 3's .label is a badge; daisyUI's is a form label. Not a visual difference — an opposite meaning, on a class that appears in both worlds. Rename all 7 label / label-* sites to badge as its own first commit, including the interpolated "label label-#{order.status.style}" at orders/_list.html.haml:60 (§3.3 — Tailwind's scanner cannot see it, and neither can a grep for the literal class).
progress is a markup rewrite Bootstrap is a nested div.progress > div.progress-bar with an inline width; daisyUI drives a real <progress> element. Renaming classes cannot get there — the change is in progress_bar_helper.rb.
modal cannot be a shim swap daisyUI is <dialog> + showModal(); the Bootstrap 3 plugin toggles .in/.fade and reads $.support.transition. Both claim .modal. So the modal component lands together with dropping the plugin — phase 7's native-<dialog> item pulls forward into this migration rather than following it. Test against modal_create.js's four flows, as phase 5.8 already requires.
tooltip goes the same way, and takes the npm dep with it daisyUI's tooltip is CSS-only, so it retires the plugin and the ~20 data-toggle="tooltip" sites. With modal, tooltip, button and alert gone, the bootstrap npm package can be dropped outright — which closes the moderate npm audit finding recorded in phase 2b.
Forms and tables are emitted centrally The single biggest lever in the plan. dry_crud/form/builder.rb, table_helper.rb and dry_crud/table/builder.rb generate almost all of it — three files instead of 49 .form-group and 37 .table view sites. Verify at the builder, not view-by-view, exactly as phase 5.5 says.

5. Step 5 — the per-component loop

Unchanged from phase 5: write the component, delete the corresponding section from whatever Bootstrap is left, check /design_guide plus that component's views, commit. One component per commit — that is what makes a regression bisectable.

#ComponentNotes
1label → badgea pure rename, no daisyUI needed yet; do it first so the class name is free before daisyUI claims it
2tablesthe app-owned .table-striped decision lands here, and it is the most visible diff in the migration
3buttonswatch .btn.disabled vs the app's own .disabled in puzzletime.scss — same trap as phase 5.4
4alerts, panels, wells, progress, list-group, close progress is the markup rewrite above; panel/well have no one-to-one daisyUI equivalent, so this is where the redesign becomes visible
5formslargest surface, but changed at the two dry_crud builders
6navs, navbar, breadcrumb, pagination pagination still targets Kaminari's default markup, not Bootstrap's (§2) — and daisyUI's pagination wants classes on the individual links, so a Kaminari view theme is likely the honest answer rather than a selector shim
7modal + tooltip Last, and together with dropping the Bootstrap JS plugins and the npm package.
8the leftovers delete the rest of bootstrap-frozen.css, the bootstrap layer, and the phase-5 shims that daisyUI has replaced
—gridnot daisyUI's job at all — it has no grid system. row/col-* → Tailwind utilities stays phase 7 work, independent of this migration

Grep test/ for .btn / .modal / .alert / .table / .label inside each component's own commit, not as a cleanup pass afterwards. The 21 Cuprite integration tests select on these class names; a test fixed three commits later is a commit that was never actually green.

The verification machinery is reused unchanged, and that is most of why this is cheaper than it looks. The full suite as every gate (1515 tests, 1m29s across 16 workers), js_errors on by default, the side-by-side servers against master, and /design_guide as the acceptance page. All of it was built in phases 0–4 and none of it needs to change. See phase 0 for the pre-flight checks and the traps around running the gate.

6. Three things to decide, not discover

The app owns its own .table-striped. Phase 1 found it at components/_table.scss:64: the real PuzzleTime three-tone column shading (#ffffff/#fcfcfc/#f5f5f5) plus a .table-hover.table-striped rule, distinct from Bootstrap's single nth-of-type rule. daisyUI's zebra striping therefore collides with app CSS, not vendor CSS — so it is a design decision (keep the Puzzle shading, or adopt zebra), not a mechanical swap. And /design_guide, the acceptance page, is precisely a table-styling gallery (D1). Expect this to be the most looked-at diff of the whole migration.

selectize.bootstrap3.scss becomes a visible orphan. It survives phase 6 as app SCSS and consumes our Bootstrap variables. Bootstrap-3-styled dropdowns sitting next to daisyUI inputs read to a user as a bug, not as deferred work — so it needs a scheduled slot in this migration (Tom Select, or a restyle against the theme), not a phase-7 bullet. Note that retiring selectize also clears the critical-but-unreachable minimist audit finding from phase 2b.

Explicitly unchanged

  • Grid — daisyUI has none; row/col-* → Tailwind utilities remains its own phase-7 item.
  • Glyphicons — D2 stands: vendored font now, inline SVG as tracked follow-up. daisyUI does not ship icons and does not change this.
  • layouts/mailer.html.haml — e-mail needs inline CSS. Do not touch it, in this migration or any other.

7. Sequencing note — worth deciding before phase 5 continues decided

Resolved 2026-08-21 as (a) — finish the shim by hand. daisyUI is not part of the asset-pipeline migration. See D5 in upgrade.html for the reasoning; the short form is that (b) would have put a visual redesign on the critical path of a Ruby 4.0 / Rails 8.1 branch that already carries a production release gate, and that daisyUI's coverage of the six contested components is only partial anyway (no panel, no well, progress is a markup rewrite, pagination wants a Kaminari view theme).

This document is not dead — it is the plan for afterwards, on its own branch, once task/65394-ruby-and-rails-upgrade merges. Steps 1–5 and the three decisions in §6 all still hold; what changed is only when. Read the fork below as the record of a road not taken rather than as an open question, and note that phase 5 will by then have shipped the hand-written shim layer these components would replace.

Phase 5 is 1 of 8 done, and 6 of the 7 remaining components (all but the grid) are precisely daisyUI's surface. Finishing them by hand means authoring roughly 500 lines of Bootstrap-look CSS in order to delete it again.

So there is a real fork, and it is cheapest to take it now rather than after phase 6:

  • (a) Finish phases 5–6 as planned, daisyUI later. Clean, fully reversible, no design sign-off needed today — at the cost of writing the shim layer twice.
  • (b) Make daisyUI the shim layer. Same per-component loop, same gates, same bisectability; the output is a component library instead of a dead end. Requires the design sign-off up front, and pulls the modal and tooltip plugin work forward out of phase 7.

(b) is the better trade if the design decision is gettable. If it is not — or if the answer is "not this quarter" — take (a) without hesitation and treat this document as the plan for afterwards. What must not happen is phase 5 finishing while the daisyUI question is still open, because that is the one path that pays for both.
