3. Cascade layers & the Preflight / Bootstrap-reset question

This is the part that decides whether a step-by-step migration is pleasant or miserable, so it is worth getting exactly right before writing any shim.

3.1 Unlayered CSS beats layered CSS — always

Tailwind 4 puts everything it emits into cascade layers:

/* what `@import "tailwindcss"` actually expands to */
@layer theme, base, components, utilities;
@import "tailwindcss/theme.css"     layer(theme);
@import "tailwindcss/preflight.css" layer(base);
@import "tailwindcss/utilities.css" layer(utilities);

Any stylesheet not in a layer outranks every layered rule, regardless of source order or specificity. If we ship the frozen Bootstrap CSS as a plain <link>, then .btn from Bootstrap beats every Tailwind utility and every shim we write, forever. The migration would stall on step one.

Therefore: give Bootstrap its own named layer, ranked between base and components.

/* app/assets/tailwind/application.css */
@layer theme, base, bootstrap, components, utilities;

@import "tailwindcss/theme.css"     layer(theme);
@import "tailwindcss/preflight.css" layer(base);
@import "./bootstrap-frozen.css"    layer(bootstrap);   /* shrinks every phase, then dies */
@import "tailwindcss/utilities.css" layer(utilities);

That single line buys us the whole step-by-step property we want:

  • Tailwind utilities and our shims (@layer components) override leftover Bootstrap without !important — so a page can be migrated before its Bootstrap section is deleted.
  • Bootstrap's own normalize.css outranks Preflight, so the reset question below mostly answers itself.
  • Our compiled application SCSS stays a separate, unlayered <link> and therefore keeps winning over everything — exactly the ordering it has today, where it is concatenated after Bootstrap.

3.2 Preflight vs. the Bootstrap reset — the actual collision list

Because Bootstrap sits in a layer above base, every rule the two resets both touch resolves in Bootstrap's favour, and the two agree on most of it anyway (box-sizing, border-collapse, font: inherit on form controls, ::placeholder, headings, hr, abbr, a colour). The residue is only the handful of things Preflight resets and Bootstrap 3 never restores:

Preflight ruleWhat breaksFix
ol, ul, menu { list-style: none } Bootstrap only sets margins on lists, never list-style-type. Bullets vanish in validation error lists (.help-block ul), layouts/_notification, dd.value ul, configurations/_group. @layer base { main ul { list-style: disc } main ol { list-style: decimal } } verify
img, svg, canvas … { display: block } Bootstrap leaves images inline. Affects layouts/_headerbar (logo.svg next to text), expense receipt thumbnails (.img-responsive), inline icons in table cells. @layer base { img, svg { display: inline-block; vertical-align: middle } }, then opt into block where wanted verify
* { border: 0 solid } Any <input>/<select>/<textarea> that does not carry .form-control loses its border. dry_crud's builder adds .form-control to virtually everything, so this should be a short list — but it needs an actual audit, not an assumption. audit step, not a blanket rule audit
* { margin: 0; padding: 0 } Bootstrap restores margins for p, headings, ul/ol, dl, dd, fieldset, legend, blockquote. none needed ok
a { color: inherit; text-decoration: inherit } Bootstrap's a { color: $link-color } wins — until Bootstrap is deleted in phase 6, at which point every link turns black. link colour must be part of the shim from day one, not an afterthought plan
html { font-family: --default-font-family } (theme layer) Bootstrap's body { font-family: … } outranks it; set Roboto in @theme anyway so the two never disagree. --default-font-family: Roboto, … ok

Conclusion: keep Preflight enabled from the very first Tailwind commit. With Bootstrap layered above base the collision surface is two rules plus one audit — and every shim we then write is authored in the world it will finally live in. The alternative (Preflight off until the end, then flip it) converts a two-rule problem into one big-bang regression at the worst possible moment.

Escape hatch if the audit surprises us: drop the @import "tailwindcss/preflight.css" line — the other three imports keep working unchanged.

pgrep -f matches the shell that is running the pgrep. Its pattern is compared against whole command lines, and your command line contains the pattern. So pgrep -f 'chrome.*--headless' | xargs kill -9 is a script that kills itself: it exits 1, prints nothing, and never reaches the next line — which looks exactly like the test command failing. The same self-match silently inflates every count you take this way.

$ ps -eo pid,etime,args | awk '$3 ~ /chrome$/ && /--headles[s]/ { print $1, $2 }'
$ ps -eo pid,args        | awk '/paralle[l]_test/ { print $1 }'

Each ui/widgets/*.js is define([ "jquery", "./menu", "../widget", … ], factory) or a bare factory( jQuery ) fallback. esbuild is not an AMD loader, so every widget takes the fallback and its dependencies are never pulled in: $.widget stays undefined, the first widget throws, and the throw takes the whole entrypoint with it. jquery-ui-rails resolved this chain through //= require; here it must be listed explicitly and in order — version, keycode, position, unique-id, widget, widgets/mouse, widgets/menu — before datepicker/autocomplete/selectable. Adding a widget later means adding its dependencies too.

3. Three plugins read the global jQuery at execution time rather than importing it: bootstrap/js/* (+function ($) { … }(jQuery)), waypoints (var $ = window.jQuery) and jquery-ujs. The last is the dangerous one — if (window.jQuery) { init(jQuery) } else { module.exports = init }, so with no global it silently exports a no-op and every data-method, data-confirm and ajax:* handler in the app quietly stops existing. Hence ./jquery_global as its own module, imported first.

4. Sprockets directives survive inside the migrated files as dead comments. modules/checkbox/{all_checker,element_hider,input_enabler}.js each carried //= require ./toggler and each subclasses app.checkbox.Toggler at load time. Under esbuild the directive is a comment, so with the modules imported alphabetically all_checker runs first and dies with app.checkbox.Toggler is not a constructor. Grep the migrated tree for //= require and turn each one into a real import. The same latent assumption exists without a directive: order_autocomplete and work_item_autocomplete extend app.Autocomplete and only worked because require_tree happens to sort autocomplete first — made explicit too.

Globals are load-bearing. Confirmed by grepping app/views/**/*.js.haml: those responses execute in global scope and use App (11×) and Modernizr (1×), plus $(…) 43× and Chart in the inline content_for :javascript blocks. Under Sprockets everything shared one scope; under esbuild each file is a module, so $, jQuery, App, Selectize, Chart and Modernizr all have to be reattached to window. Waypoint looks like a seventh but is only ever a local variable name.

A quick way to check all of it at once is a throwaway integration test that page.evaluate_scripts the typeof of each global and the loaded document.scripts — that is what located trap 1. Remember to visit a page first: several test classes override login to visit one, and the bare helper only signs in, so a probe using it inspects about:blank and reports everything as undefined.

Pre-existing defect to carry over: bootstrap/transition is missing today. application.js.coffee requires modal, tooltip, button, alert and collapse but never transition. Verified in a running browser: jQuery.support.transition is empty and jQuery.fn.emulateTransitionEnd is undefined.

Root cause: requests outliving their test, with DatabaseCleaner truncating underneath them. PATCH /plannings/orders/978000142  status:0  duration:359256ms  db:359231ms

end
